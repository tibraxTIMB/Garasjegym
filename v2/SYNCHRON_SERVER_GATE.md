# SYNCHRON – server integration gate
Status: design and tested in-process contract only. No database change, deployment, or live notifications approved under DOPPELADLER_MANDATE.md.

## Required host
- Reuse existing account authentication. Derive actor from verified access token on the server, never request JSON, user-editable metadata or UI role.
- Verify active membership, coach assignment and WOD visibility on creation. Recheck access and membership on every command/read, including after revocation.
- Persist session and invitation outbox atomically. Unique session ID and (session ID, recipient) key; duplicate same request returns same ID, conflict rejected. Dispatch only to recipient via existing notifications system; deliver/retry idempotently. No new anonymous public endpoints.
- Atomic compare-and-swap on session revision for every transition. Keep internal state private; return only actor-scoped projection. Do not expose full session, other doses, save tokens or service credentials to browser.
- Client adapter uses existing authenticated transport, not browser-local storage. No automatic repeat of a mutation with uncertain result; fresh snapshot and same request ID where appropriate.
- Reserve and write individual logs only server-side, using sealed payload and stable unique token per member/session. Verify RPC compatibility and receipts before enabling.
- Realtime should convey scoped state or invalidation only; reconnect fetches authoritative snapshot. Polling in dev panel is not a production scaling decision.
- Test on isolated test data with explicit permission, RLS/access and concurrent writes, revoked accounts, two real devices, notification retries, network loss, actual log idempotency and rollback. No migration or production deployment until reviewed.
- App runtime prop is null by default. Do not supply it until host authentication, atomic persistence, access controls and end-to-end tests are verified. Existing local workouts must not be replaced by a Synchron invitation. The runtime dispatcher supports create/snapshot/command only; server-side reserve and writer remain separate.

## Explicit authorization adapter (GW03 finalization)
The trusted dispatcher disables creation/snapshot/command when `authorizeSession` is absent. The host callback receives `{actorId,sessionId,operation,revision}` and must return literal `true` only for current valid access; no user-provided actor accepted. Gateway rechecks before mutation and before returning a newly committed projection. Host `compareAndSwap(sessionId, revision, next, actorId)` must enforce current permissions atomically in the same transaction, not trust the earlier callback; host `createAtomic` must similarly check current creation and exclusive participation. This is not a real persistence implementation. Direct gateway without callback is retained for pre-authorized in-process test fixtures only; never mount it as production transport. Revocation fixture tests do not establish live RLS or concurrency safety.

## Active session discovery contract (GW03)
Optional `discover` operation takes no session ID, member ID or credential in JSON. The trusted host must provide `authorizeDiscovery(actorId)` and `readActiveSession(actorId)`, with current account/membership authorization and a transactional exclusive-session index. Return a single session ID only for an active leader or joined member; return literal `null` only for authoritative absence. Conflicts, unavailable DB and unknown results must throw or return invalid data (never `null`). Gateway rechecks discovery authorization and actor-scoped snapshot authorization. Runtime exposes discovery only with explicit `discoveryEnabled:true`. Discovery does not write, release locks, or automatically mount the live panel; App remains disabled until a real host and verified device re-entry policy exist. A fixture is not persistence or end-to-end evidence.

## Isolated durable persistence rehearsal
The `scripts/synchron-persistence.test.mjs` fixture uses Node 22 SQLite in a disposable OS temporary directory, two independent connections, synthetic identities, explicit account/coach/roster lookup, transactional session/outbox creation, revision CAS, exclusive leader/joined slots, restart, revocation between authorization and write, retry and rollback. It is test-only, never imported by app/Edge Functions, does not use Supabase or real credentials, and is not a substitute for the production Postgres transaction/RLS/verified JWT adapter. Invitations may coexist before join; exclusive occupancy is enforced atomically at join, and slots are removed on finish. Current fixture conservatively blocks new mutation if an occupied participant is revoked; actual incident recovery needs a separately reviewed termination policy. No real deployment or migration.

## Guarded App re-entry (opt-in)
App runs bounded discovery only for an explicitly injected matching runtime and an approved profile, outside Tablet Lab. Unknown/pending discovery blocks new launch intents; existing local session/draft remains accessible. Recovered authorized live snapshot binds the route to the current actor/runtime. Local session takes precedence; user can return to the recovered session after local completion. Failed discovery offers explicit retry, does not turn error into absence, and does not clear local storage. No production runtime is injected. Browser-level re-entry, real cross-device races, and production host remain unverified.

## Authenticated HTTP boundary (candidate, not deployed)
`server/synchronHttp.js` binds each POST to a verified bearer identity, rejects unknown origins/methods/content types/oversize bodies and does not cache responses. Its host factory is trusted server-only; a real Supabase host must verify via `auth.getUser(token)` (not user metadata) and bind current membership/session authorization to Postgres transactions. `synchronHttpClient.js` uses the existing SDK's fixed `synchron-live` invocation, with explicit opt-in, current account/token checks before and after the request, bounded waiting and no automatic command replay. The SQLite persistence rehearsal now uses these actual Request/Response boundaries with synthetic verified credentials. No deployed function, real JWT verification, production PostgreSQL or runtime injection. HTTP handler does not expose raw reservation data or credentials. Production CORS configuration and auth/session revocation tests still required.
