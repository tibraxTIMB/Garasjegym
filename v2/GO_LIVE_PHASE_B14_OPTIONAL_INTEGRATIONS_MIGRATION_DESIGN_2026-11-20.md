## 2. Calendar and WOD favorites

The test migration `20261117123639_wod_favorites_calendar_and_assigned_visibility.sql` creates per-user WOD favorites and an admin/manager calendar.

Production adaptation requirements:

1. `wod_favorites` must enforce user ownership and unique (user_id, wod_id); members can only add/remove their own favorites.
2. Favorite insertion must validate that the WOD is visible to the member (published or assigned PT WOD) and that the member is active/approved.
3. The test policy currently allows admin/manager deletion across users. This is unnecessary for personal favorites and should be restricted to the owner unless a concrete support workflow requires otherwise.
4. Calendar event creation currently requires admin/manager. Define whether PT coaches need calendar write access and scope it to assigned clients only; do not grant all coaches broad calendar visibility.
5. Validate event ownership, client visibility, class/PT FK behavior, timezone handling, and date range constraints.
6. Calendar event links must not expose private PT appointment details to members who are not the client or assigned staff.

## 3. Notifications

The source migrations add recipient-scoped notifications and several trigger-driven event rules.

Production requirements:

- A member can read/update/delete only their own notifications.
- Staff insert permissions must be limited to explicit roles; ordinary users must not forge notifications for another recipient.
- Trigger functions must derive recipients from trusted booking/session/order rows, not caller-supplied IDs.
- Notifications must not leak client names, notes, private appointment titles or booking details to unrelated members.
- Add idempotency/deduplication keys for events that can be retried or generated by multiple triggers.
- Notification creation must not make the primary transaction fail unexpectedly unless that is an intentional product rule.
- Ensure trigger search_path is fixed and grants do not allow anon invocation.
- Realtime publication must be limited to the recipient's own rows and validated under RLS.

The migrations include multiple overlapping PT and class notification rules. Reconcile them into one event matrix before production; avoid duplicate messages from legacy triggers plus new event rules.

## 4. Coffee bar

The source migration defines products, orders, order items, member ordering RPC, staff order updates and notification triggers.

Production requirements:

1. Preserve order-item snapshots (`product_name`, `unit_price`) even if a product is later renamed or deactivated.
2. Only active members can order; prices must always be read from the trusted product row, never from client-supplied values.
3. Validate quantities, note length, item count, duplicate product lines and order total calculation.
4. Member reads are own-orders only; staff updates are restricted to allowed status transitions.
5. Prevent a member from changing `member_id`, `total`, item price or order status directly.
6. Product writes and order management must be admin/manager only.
7. Reconcile old/new coffee RPC variants and skip/review triggers so the same order cannot be charged/recorded twice.
8. Define retention and deletion behavior before cascading order items or removing a member profile.
9. Trigger notifications must not leak customer details to unauthorized staff or members.

## 5. Social reactions and privacy-safe infotainment

Production already has an empty `social_posts` table with a JSONB reactions column. The test `toggle_social_reaction` function locks the post row and validates active membership, which is a sound atomicity foundation.

Before release:

- Confirm social post read/insert/update/delete RLS and restrict authors to their own posts.
- Validate that a member cannot forge or remove another member's reaction.
- Bound reaction JSON size and prevent malformed or duplicated user IDs.
- Ensure the UI displays counts without exposing unnecessary member identity lists.
- Confirm author role changes do not rewrite historic authorship unexpectedly.

Infotainment schedule must return only published group classes and anonymized PT busy slots. It must never expose PT client IDs, names, notes, private appointment titles or internal record identifiers. The privacy-safe event key migration should be used, and the earlier function definition that returned raw class/PT IDs must not be restored by a later migration.

## 6. Proposed migration order

1. **Calendar/favorites foundation:** after membership, class and PT foundations; role/RLS tests first.
2. **Notification core:** recipient-only RLS, trigger helpers, event idempotency and realtime validation.
3. **Coffee bar:** products, orders, atomic order RPC, status transitions and notifications.
4. **Social hardening:** existing posts contract, reaction RPC and author ownership.
5. **Infotainment:** privacy-safe read model only after class/PT publication and privacy rules are stable.

Each unit needs preflight and postflight assertions, explicit grants, fixed search_path for privileged functions, app round-trip tests, member-to-member isolation tests and a tested recovery path.

## 7. Execution boundary

Only source review and live read-only production catalog/count queries were performed. No DDL/DML, policies, functions, triggers, realtime publication, Auth settings, secrets or deployment were changed.

**B14 result:** Integration dependencies and privacy requirements are documented. Production has none of the new V2 calendar/notification/coffee/favorites/PT-program tables; the existing social_posts table is empty and structurally has the reaction payload column. Release remains **NO-GO** pending backup/PITR evidence, isolated restore, complete migration rehearsal and explicit owner authorization.
